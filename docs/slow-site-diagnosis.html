Why every page of your WordPress site is slow

A site that is slow everywhere is a different problem from a site with one slow page. Four measurements separate the usual causes: time to first byte, HTML size, image weight, and query count. Cinder Page Cache records the last three for you and caches the first out of existence once pages are warm.

The order to fix them in

Cache first, because it removes the render cost entirely. Then HTML size, then images, then the database. Doing them in the other order produces a faster page that is still rendered on every request.

Measurement 1 — time to first byte

Above roughly 600 ms on a cached page, the server is the problem: no object cache, an overloaded host, or PHP doing work per request that should be done once. A page cache turns this into a file read, which is the single largest win available on shared hosting.

Measurement 4 — the database

Revisions, expired transients, orphaned metadata and spam comments all sit in the same tables every page reads. On a five-year-old site that is commonly 30–60% of the database, and cleaning it shortens every query that touches those tables.

Watch the ratio rather than the total: hits divided by requests, over a day. A cache that serves 60% of requests is doing something; 95% means it is covering the site. The same screen shows cache size and the oldest entry, which tells you whether the TTL matches how often the content actually changes.

If the ratio is high and the site still feels slow, the problem is downstream of PHP: images, fonts, or a host network that is saturated. That is the point at which a CDN becomes the right answer, and the counters here are how you know you have reached it.

Who this is for

Cinder Page Cache fits a site on one server: a blog, a brochure site, a small shop, a club site with a thousand visits a day. It is the wrong tool for a WordPress network of fifty sites with a shared object cache cluster — that needs infrastructure, not a plugin — and it is unnecessary on a site that already serves static files from a build step.

What it does not do

It will not make a slow host fast, and it will not score well on a lab test that disables caching. It does not touch other plugins' tables, does not replace Redis, and does not promise a Core Web Vitals pass on a theme that ships six JavaScript libraries. Every claim on this page is something the plugin itself performs.

Frequently asked

The dashboard shows a high hit rate but the site feels slow — why?

A hit rate only covers pages that were cached. Check whether the slow page is excluded, whether it is a logged-in view, and whether images on it are the problem.

Does caching help admin pages?

No. Logged-in requests bypass the cache by design; admin slowness is usually queries or host CPU.

How long should a cached page take?

On a modest server, 50–200 ms of server time. If it is much more, the cache is missing the request.
