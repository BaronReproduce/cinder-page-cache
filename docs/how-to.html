How to clear the WordPress cache in WordPress

Clearing the cache means deleting the stored HTML so the next request is rendered from scratch. In Cinder Page Cache that is one button on the dashboard, but the reason a clear sometimes appears to do nothing is worth knowing: a page cache sits in front of PHP, so a cleared page is rebuilt on the next visit, and any CDN or proxy in front of the site keeps its own copy. Clearing twice in a row without a visit does not produce a different result.

When the cache should stay warm

On a shop, a purge during a sale is a self-inflicted slowdown: the first hundred visitors after a full purge all render. Configure purge-on-update for content pages, leave the product archive cached, and watch the hit rate on the dashboard for a day before deciding it is broken.

Clearing one page instead of everything

A full purge is the safe habit during development and the wrong habit in production: every purge means the next visitor pays the render cost. Cinder Page Cache purges the URL that changed when a post is edited, and the whole cache only when you press the button or change a setting that affects every page, such as minification.

The three caches people confuse

WordPress has a page cache, an object cache and whatever your host put in front of the site. A page cache stores finished HTML. An object cache stores query results for reuse inside one request or across requests if a persistent backend exists. A host-level cache stores everything at the edge and is usually cleared from a hosting panel, not from WordPress. Cinder Page Cache manages the first and exposes counters for both.

If a change does not appear after clearing, check in that order: page cache, object cache, host cache. Most 'the plugin broke my site' reports end at step three.

Three numbers on the dashboard answer it: hit rate, bytes saved per request, and average generate time. A hit rate that climbs over a day of real traffic means the cache covers the pages people visit. Bytes saved moving means minification and image conversion are reaching the response. Generate time is what a visitor would have waited without the cache — if it does not drop, the pages are not being served from it.

Then confirm from outside: open the site in a private window, reload twice, and compare the server timing header before and after. A cached response is a few milliseconds of server work; an uncached one is your theme plus every active plugin. If the second reload is not markedly faster, an exclusion is swallowing the request.

Who this is for

Cinder Page Cache fits a site on one server: a blog, a brochure site, a small shop, a club site with a thousand visits a day. It is the wrong tool for a WordPress network of fifty sites with a shared object cache cluster — that needs infrastructure, not a plugin — and it is unnecessary on a site that already serves static files from a build step.

What it does not do

Frequently asked

Does clearing the cache delete my content?

No. It deletes generated HTML and stored counters. Posts, pages, media and settings are untouched; the next request regenerates the page.

Why is the site slower right after a purge?

Every cached page has to be rendered again. The first visitors after a purge pay that cost; the hit rate recovers as pages are visited.

Should I clear the cache after publishing a post?

Cinder Page Cache purges the affected URL automatically on save, so a manual purge is only needed after changing a global setting.
